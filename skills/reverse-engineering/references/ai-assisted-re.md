# AI-assisted reverse engineering

> LLM driver decompilation/multi-agent verification/neural semantic recovery
> 2025-2026 Biggest Paradigm Shift

## Core tools and models

### LLM4Decompile
- The first open source framework to use LLM for binary → source code decompilation
- Support x86/ARM/MIPS multi-architecture
- Input: Assembly code → Output: C source code
- Training data: million level source code-assembly pair

### Decaf (2026)
- **Compiler feedback verification**: Compile the source code generated by LLM → Compile → Compare the original binary
- Effect: Decompilation rate 26% → 83.9% (ExeBench Real -O2)
- Key Insight: Feedback loops are more effective than larger models

### Constraint-Guided Multi-Agent (2026)
- Three-level verification pipeline:
  1. Grammatical correctness (parsing)
  2. Compilability (GCC)
  3. Behavioral equivalence (LLM generated test cases)
- 84-97% repeatable execution rate, only $0.03-0.05 each time

### REMEND (2026)
- Specialty: Extracting mathematical equations from binary
- 89.8-92.4% accuracy (across 3 ISAs × 3 optimization levels × 2 languages)
- Speed: 0.132s/function, only 12M parameters

### Glaurung
- Open source Ghidra alternative, Rust kernel + Python bindings
- **AI native architecture**: LLM Agent is embedded in each analysis layer
- Evidence artifacts: plain/rich/JSON/JSONL multi-format output for LLM consumption
- Support: ELF/PE/Mach-O, x86/ARM/RISC-V, IOC detection, entropy analysis

## Workflow: AI-enhanced binary analysis

### 1. LLM assisted rapid reconnaissance

```text
□ strings extraction → LLM semantic classification (URL/key/path/protocol)
□ Import table analysis → LLM inference function (encryption=OpenSSL? Network=libcurl?)
□ Disassembly fragment → LLM identification mode (cryptographic algorithm, anti-debugging, virtual machine detection)
□ Error message → LLM inference context ("Invalid license" → Authorization logical location)
```

### 2. neural decompilation

```bash
# LLM4Decompile
python llm4decompile.py --binary target.so --arch arm64 --output target.c

# Verification results (recompile + compare)
gcc -O2 -o target_recompiled target.c -fPIC -shared
# → Verify output behavioral equivalence
```

### 3. Multi-Agent Authentication

```text
Agent 1 (syntax): Check whether the generated C code can be parse
  ↓ Failure → Feedback error message to LLM and try again
Agent 2 (compile): GCC compile → check warnings/errors
  ↓ Failure → Feedback compilation error to LLM
Agent 3 (behavior): LLM generates input → runs original and recompiled version → compares output
  ↓ Inconsistency → Feedback differences to LLM → Iterative correction
```

### 4. LLM assisted static analysis

```text
□ Function renaming: Enter decompiled pseudocode → LLM suggests semantic names
□ Type recovery: Analysis context → LLM inferred structure/class definition
□ Algorithm identification: assembly fragment → LLM identification cryptographic algorithm (AES/TEA/RC4/custom)
□ Protocol reversal: network packet sequence → LLM infers protocol format
□ Comment generation: decompile code → LLM generates Chinese/English comments
```

### 5. macOS/iOS Private Framework Reverse (MOTIF)

```text
Problem: macOS private framework has no documentation and type information is missing
Scenario: LLM Analysis Usage Pattern → Infer Method Signatures and Parameter Types
Effect: ObjC signature recovery 15% → 86% (vs static analysis)
```

## LLM prompt template

### Function semantic analysis

```
You are a reverse engineering expert. Analyze this decompiled function:

[pseudocode]

1. What does this function do? (one sentence)
2. Suggest a meaningful function name.
3. What are the input parameters and their likely types?
4. What is the return value?
5. What external APIs/functions does it depend on?
6. Any security-relevant operations (crypto, auth, network, file I/O)?
```

### Algorithm identification

```
Analyze this assembly/disassembly for cryptographic operations:

[Assembly code]

1. Is this a known cryptographic algorithm? (AES/DES/RC4/TEA/ChaCha20/custom?)
2. Identify the key schedule and round structure.
3. What is the key size?
4. Are there any hardcoded constants that identify the algorithm?
```

### Protocol format inference

```
Given this network packet sequence, infer the protocol structure:

[hex dump]

1. Identify magic bytes and length fields.
2. Propose a struct definition for the packet header.
3. What field(s) appear to be checksums/CRCs?
4. Is this a known protocol or custom?
```

## Tool selection

| Scenario | Recommended Tools | Cost |
|------|---------|------|
| Fast decompilation | LLM4Decompile | Free (local GPU) |
| High-precision decompilation | Constraint-Guided Multi-Agent | ~$0.05/binary |
| Math Function Extraction | REMEND | Free |
| Full platform RE | Glaurung (Rust) | Free and open source |
| LLM interaction | Claude API / GPT-4 / DeepSeek | ~$0.01-0.10/time |

## limitation

- **Complex Control Flow**: Virtualizing/obfuscating code remains difficult (control flow flattening, VMProtect)
- **Indirect call**: The virtual function table and function pointer are difficult to restore
- **Inline functions**: Boundaries are blurred after compiler inlining
- **Floating point operations**: The semantic recovery of vectorized instructions needs to be improved
- **Context Window**: Large function (>1000 lines) exceeds LLM context limit
