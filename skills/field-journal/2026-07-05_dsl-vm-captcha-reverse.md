# Complete reverse analysis of the verification code system

## scene
Goal: Reverse a large-scale verification code system to understand its complete working principle and verification process.

## target entity
- **nc.js** (72KB) — Webpack-packaged slider core (9 modules)
- **fireyejs.js** (583KB) — DSL VM interpreter (26 opcode custom instruction set)
- **awsc.js** (9KB) — module loader
- **secaptcha.js** (72KB) — WASM C compilation product (emscripten)
- **et_f.js** (262KB) — Another DSL VM type file

## Proven technical solutions

### Solution A: Selenium + CDP drag and drop (recommended)
Verification is done in a real browser by sending native mouse events via CDP`Input.dispatchMouseEvent`.
- Success rate: high
- Dependencies: Chrome + Selenium/Playwright

### Option B: Playwright Headless Browser Runner
Load the DSL VM and module loader in Playwright, exposing the token via the HTTP API.
- Success rate: Medium (depends on WASM initialization environment)

### Solution C: Pure requests protocol verification
Verify by calling the API endpoint directly via HTTP request.
- Success rate: **very low** (token is strongly bound to browser TLS/IP/fingerprint)
- Not recommended

## Key findings

1. **Token cannot be used without the browser** — When the token generated by the DSL VM is submitted, the server will verify the context consistency (TLS JA3, IP, Cookie, Referer, etc.)

2. **fireyejs.js is not a WASM binary but a DSL VM** — 583KB custom virtual machine implemented in pure JS, which loops through the 26 opcode interpreter to execute the encoded instructions

3. **nc.js 9 module is 100% reverse engineered** — includes API endpoints, slider UI, interaction logic, ncSessionID algorithm, multi-language, and more

4. **The real WASM compilation product is secaptcha.js** — 72KB, using SharedArrayBuffer + Atomics, emscripten compiled C code

## Trampling on pit records

1. Testing appkey will not trigger real verification, you must use the appkey of the real page
2. Returning a specific status code of`initialize`is the slider mode, returning`success`is just a confirmation of session creation.
3. The URL events of JSONP requests in the performance log may be incompletely captured due to the script tag injection method.
4. The exported function name does not exist in the DSL VM file (encoded by the VM), the real export is exposed through the module registry

## Reusable mode

- **DSL VM reverse mode**:`case extract → opcode classification → constant table analysis → function tracing → extract exported functions`
- **General architecture of verification code system**:`entry pointJS → module loader(WASM/DSL) → APIcommunication layer → frontendUI → server-side validation`
- **CDP native event bypass**:`Input.dispatchMouseEvent`bypass detection, not related to WebDriver

## tool chain

- Selenium + CDP: Browser Automation + Native Mouse Events
- Playwright: Headless browser + route interception
- Python requests: pure API call (validation failed)
- Node.js + Playwright: Runner service
