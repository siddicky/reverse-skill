# .NET Reverse Engineering Universal Workflow

Full workflow details, IL patch reliability, string decryptor extraction, state machine identification, dnlib scripting.

## Complete workflow (end-to-end)

```text
1. Identify → Confirm that it is a .NET managed program (not native)
2. Detect → DIE / de4dot --detect identify obfuscators
3. Deobf → de4dot deobfuscation (retain the original sample)
4. Static → dnSpyEx browses C# view positioning, IL view looks at key logic
5. Dynamic → dnSpyEx debugger breaks in the key method and sees the runtime plain text
6. Patch → IL editor modification, Save Module
```

The products of each step must be placed on the disk: original sample`target.exe`→ shelled`target-clean.exe`→ patched`target-patched.exe`.

## IL patch vs C# patch reliability

**Core conclusion: Use the IL editor for critical modifications, not the C# editor.**

| Dimension | C# Editor (Edit Method C#) | IL Editor (Edit IL) |
|------|---------------------------|---------------------|
| Compilation failure risk | High (missing references, syntax, lambda rewriting failure) | Almost zero |
| Information fidelity | The compiler regenerates IL, which may be different from the original IL | Replaces the original, changing instruction by instruction |
| is applicable to |. Change a string, change a constant, simple logic. | change judgment, delete verification, change control flow. |
| async/await/state machine | often fails to compile or is distorted | directly changes the state machine fields, reliable |

dnSpyEx's C# decompiler is based on read-only decompilation + attempt to recompile, and recompiling the code generated by the compiler (state machine, closure,`yield`) can easily fail. The IL editor is instruction-by-instruction editing, what you see is what you get.

### Typical IL patch pattern

```text
Change condition (if (check) → always true）：
  Original: : call bool Foo::Check()
      brfalse.s SKIP
  change: ldc.i4.1            ; push true
      brfalse.s SKIP      ; It now never branches; SKIP is not executed
  Or more directly:
      ldc.i4.1
      ret                 ; Have the method return true

Change condition (if (check) → always false）：
  ldc.i4.0
  ret

Delete the entire verification section:
  Replace all instructions with nop，or change it to ret + the correct return value

Change string constant:
  C# Changing strings in a C# editor is usually OK（ldstr a direct token replacement token），but if the string is in a resource or encrypted,/the decryption logic must be changed

Change numeric constants:
  ldarg / ldc Modify the operands of ldarg/ldc instructions directly
```

## State machine identification (async/await/yield)

C#'s`async/await`and`IEnumerator`yield are compiled into a **state machine**: the compiler generates a nested class, and the`state`field is used for switch dispatch in`MoveNext()`. The dnSpyEx C# view will be restored to async, but decompilation may cause distortion. The IL view is most accurate when looking at`MoveNext`.

```text
MoveNext structure of async/await:
  switch(this.<>1__state) {
    case 0: ... await logic before await; this.<>1__state = 1; await MoveNext;
    case 1: ... await logic after await;
  }

To patch async logic: change the state transfer in MoveNext or the judgment in a specific case.
Changing the C# editor to async will almost certainly fail → IL must be used.
```

## String decryptor extraction

See`obfuscators.md`for details. Here is the addition of dnlib scripted batch decoding of strings:

```csharp
// dnlib script: scan all string decryptor calls, write back after runtime restoration
// Usage: dotnet script decrypt.csproj target.exe 0x06000012
using System;
using System.Reflection;
using dnlib.DotNet;
using dnlib.DotNet.Writer;
using dnlib.DotNet.Emit;

var module = ModuleDefMD.Load(args[0]);
var decryptorToken = uint.Parse(args[1], System.Globalization.NumberStyles.HexNumber);

// Find the decryption method and call it using reflection (the assembly needs to be loaded into the AppDomain)
// Traverse all methods and replace call Decryptor(token) with ldstr "decryption result"
foreach (var type in module.GetTypes())
    foreach (var method in type.Methods)
    {
        if (!method.HasBody) continue;
        var instrs = method.Body.Instructions;
        for (int i = 0; i < instrs.Count; i++)
        {
            // Identify the call decryptor mode, call the decryptor to get the plaintext, and replace it with ldstr
            // (The template for calling the decryptor by reflection is omitted here. The idea is: load the original assembly →
            //   MethodInfo.Invoke get plaintext → instrs[i] = OpCodes.Ldstr + operand=plaintext)
        }
    }

var opts = new ModuleWriterOptions(module);
module.Write("target-decrypted.exe", opts);
```

dnlib is the de facto standard for .NET metadata programming and is used internally by de4dot. Preferred when writing custom deobfuscation scripts.

## Key points of dynamic debugging

The dnSpyEx debugger is much more friendly to .NET programs than native:

- **Breakpoint is at the method entrance**: Right-click the method → ​​Add Breakpoint
- **Look at the object value**: After stopping, the Locals / Watch window can directly look at the object fields and string content.
- **Memory writing**: You can directly change the runtime variable value (Edit Value)
- **Exception breakpoint**: Debug → Exceptions, check the exception type to be broken - the confusion is commonly used to drive the control flow, and you can see the real path if you break the exception.

### Exception driven control flow

Some obfuscators stuff normal logic into`try`and use`throw`+`catch`to make jumps. When viewed statically, IL looks like exception handling, but it is actually control flow:

```text
try { throw new CustomException(0x42); }
catch (CustomException e) {
    switch(e.Code) {
        case 0x42: actual logicA; break;
        case 0x43: actual logicB; break;
    }
}
```

Set an abnormal breakpoint (break`CustomException`) and track the value flow of`Code`, which is faster than hard-coding IL.

## Module initializer (Module.cctor)

The static constructor of the`.NET`module (`<module>`'s`.cctor`) is executed first when the assembly is loaded. The obfuscator often puts anti-tamper/decryption initialization here. Analysis order:

```text
1. First look at <module>.cctor (Module .cctor) - decryption/anti-debugging initialization
2. Look again at Program.Main/Startup
3. anti-tamper is in .cctor → patch .cctor first and then unpack it
```

## Generic mode for extracting configuration/C2/Key

Red team tools and loaders often embed configuration encryption in resources or fields and decrypt it at runtime:

```text
Positioning process:
1. strings to see if there is a clear text URL/IP (usually not after obfuscation)
2. Find byte[] field + the decryption method (AES/XOR）
3. Dynamic break at the return point of the decryption method, dump the decrypted plaintext
4. Common case: AES-256-CBC with Key==IV（Codegate 2013 pattern; see reverse-engineering/tools.md .NET section)
```

Refer to the specific configuration structure of the red team tool in`references/sharp-tools.md`.

## Boundary with reverse-engineering

- **IL2CPP / NativeAOT** → Compile to native, no CLR metadata → Use`reverse-engineering/`(IDA/r2), this skill only does recognition
- **Hosted .NET** (standard C# exe/dll, Mono/Unity hosting layer, Xamarin) → this skill
- **Mixed (native loader + .NET payload)** → The loader part is`reverse-engineering/`, dump the .NET payload and then cut the skill
